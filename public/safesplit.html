Safesplit – Secure Expense-Splitting App

Course project · ICT2216 Secure Software Development, SIT · May–July 2026 · Development phase

Role
Software engineering developer
Team
7 (software engineering and information security students)
Stack
React, Node.js with Express, PostgreSQL, Docker Compose, Nginx, AWS EC2
Pipeline
GitHub Actions (unit tests → Selenium tests → deploy)

The app

Splitting shared costs among friends, flatmates or travel groups usually means a spreadsheet or a chat thread nobody trusts. Safesplit lets users create groups, log expenses split equally, by percentage or by custom amounts, and see a live summary of who owes whom. Debts are settled outside the app (cash, PayNow, bank transfer) and then recorded, with the other person confirming receipt, so both sides agree on every balance. A full history of expenses and settlements keeps the group transparent, and expenses can be logged in different currencies.

How the team worked

The module paired software engineering students, who built the application, with information security students, who led the security analysis. Security was designed in from the start: the team derived security requirements from the functional ones, paired each use case with a misuse case, ranked risks, and built a STRIDE threat model before implementation began.

Architecture

Key security choices in the implementation:

  • Passwords hashed with bcrypt (cost factor 12), each with its own random salt.
  • Sessions use signed tokens backed by a server-side session record, so a session can be revoked immediately, for example on logout.
  • All input validated against schemas, and all database queries parameterised.
  • Login and other sensitive endpoints are rate-limited.
  • The database has no public port; only the web server accepts outside connections.

Planned vs built

The design called for a production-style AWS setup: load balancer, managed database, separate session store and web application firewall. The course deployment ran on a single virtual machine instead, so the team mapped each planned component to an equivalent control and documented the gaps:

Planned Built Trade-off
Load balancer with managed certificate Nginx on the VM with a self-signed certificate Same encryption; only certificate trust is reduced
Managed database (RDS) PostgreSQL container with no public port Same isolation from the internet
Separate session store Sessions table in PostgreSQL Same server-side revocation, one fewer service
Web application firewall Not built Input validation covers the application layer; recorded as residual risk

What I learned

  • Building alongside security specialists changes how you write features: every endpoint started with "who is allowed to call this, and what if they send something unexpected?"
  • A pipeline that blocks deployment on failing tests makes the team trust the live site.
  • When the real environment differs from the design, the honest move is to document what each change costs, not to quietly drop the requirement.
